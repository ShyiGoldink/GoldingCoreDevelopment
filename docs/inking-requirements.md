# InkingUIKit 内置能力需求单（2026-10-22）

> 提出方：GoldingCore core 层。
> 每条都标注**现在 core 付了什么代价**——没有代价的一条都没写进来。
> 分级依据：修掉之后能**删掉多少绕路代码**，不是"用着不舒服"。

---

## 0. 先说结论

如果只能改一处，改 **A 组**。A 组四条是同一个根因，它直接决定 core 的架构复杂度：

> **渲染列表与命中表在"建树时"一次性收集，之后树变了不重建。**

core 现在因为这一条，把「请求重建整棵树」当成了万能手段（`requestRebuild`），抽屉展开、换页、弹层、换肤全走它。一旦 A 组修好，`requestRebuild` 会从"到处都要用"退化成"只有换肤用"，`HostApp` 的拆分难度会下降一个量级。

B/C 组是布局与绘制的表达力，影响插件作者的代码量。
D 组是你主动问的 test 能力——**它同时也是"SelfTest 做成插件"的前置条件**（见 §5）。

---

## A 组：树的动态性（修了能砍掉整树重建）

### A1. `InkingDynamicWidget` 不进命中表

**现状**：动态组件子树里的静态按钮永远收不到点击。`OwnsSubtreeHit` 只登记自己一条包络，往下不再钻。

**core 付的代价**：所有要响应输入的容器被迫用 `InkingStaticPanel`（`ShellPlugin` 全部改成静态容器）；而静态容器**改尺寸只能重建**，于是抽屉展开/收起（56↔200px）必须整树重建。core 的 `HostApi::requestRebuild` 因此成了高频调用，且重建会销毁所有节点 → 插件的 `g_lastPageId` 这类"跨重建状态"必须自己用静态量兜住（`ShellPlugin.cpp` 里有三个）。

**期望**：动态组件的子树也能进命中表；或显式声明"本组件参与命中"。

### A2. 事后 `AddChild` 的子树不进渲染列表

**现状**：连一块纯红面板都不画。节点在、`IsVisibleInTree()` 为真、就是不渲染。

**core 付的代价**：覆盖层（`appdrawer` 应用柜）只能"弹出即整树重建"。一个底部抽屉的显示/隐藏，代价是销毁并重建整个三栏骨架。

**期望**：`AddChild` 之后能进渲染列表；或提供 `RebuildRenderList()` 显式入口（见 A5）。

### A3. 创建时 `SetVisible(false)`，之后设 true 也不渲染

**现状**：不能用可见性开关做弹层。

**core 付的代价**：同 A2。本来"创建时隐藏、点按钮置可见"是最省的做法，现在必须"不创建 / 整体重建"。

### A4. `fillMain` 只在首次收敛

**现状**：改尺寸不能靠重排。

**core 付的代价**：同 A1。抽屉宽度动画无从谈起，只能跳变后重建。

### A5. 【建议】给一个显式的 `RebuildRenderList()` / `InvalidateTree()`

A2/A3 本质上都是"树变了但引擎的收集表没跟上"。比起逐个修 bug，**暴露一个"我这棵子树变了，请重建收集表"的显式调用**更根本，也更好测。有了它，A2/A3 可以立即有解，A1/A4 可以逐步来。

## B 组：布局表达力

### B1. 交叉轴拉伸

**现状**：布局只按主轴分配；`width=0` 的按钮解出来就是 0 宽，**不画也不报错**。

**core 付的代价**：每个容器都要显式算宽度（`1224` / `1080` / `200` 这些魔数散在 `ShellPlugin.cpp` 里），算错静默失败。core 的自检里专门有一组断言（`内容区铺满剩余宽度 == 1224`）就是在替引擎验算。

**期望**：`Fill` / `Stretch` 之类的交叉轴填充语义，或"尺寸为 0 时取父级剩余"。

### B2. `InkingDynamicWidget` 缺名字入口

**现状**：`GetName()` 有，动态组件无法设名字。

**core 付的代价**：`findByName` 走不到动态组件；自检只能按"子节点索引"定位（`main.cpp:571-589` 里 `children.front()` / `children[1]`），索引一变断言全错。

**期望**：`SetName()` 对所有 widget 基类可用。

### B3. 顶栏/菜单栏的"当前高度"可查询

**现状**：`MenuBarStyle::hideInFullscreen` 让顶栏全屏时整条消失，但宿主不知道它现在多高。

**core 付的代价**：`architecture.md` §8 记着的问题——内容区高度不能写死 `窗口高 - 40`，否则全屏留一条空白。现在 `kTopBarHeight = 40` 仍写死在 Shell 布局常量里，**这条一直没修**。

**期望**：`GetCurrentHeight()` 或 `IsVisible()` 可查，让内容区按"窗口高 − 顶栏当前高"算。

## C 组：绘制

### C1. `0x00000000` 渲染成黑块，不是透明

**core 付的代价**：要"无背景"必须填成页面底色（`GoldingPalette.h` 里为此专门提供了底色常量）。换个主题就得同步改，漏一处就是一块黑。

**期望**：真正的透明，或"不填即无背景"。

### C2. 按钮文字对齐不可控

**core 付的代价**：纯文字入口一律绕道 `InkingStaticLabel`，按钮只用来做有背景的块。

**期望**：按钮内文字的水平/垂直对齐可设。

### C3. 字体缺字符（`☰` 渲染成方框）

**现状**：已知，用 `≡` 绕过。不紧急，但插件作者会反复踩。

## D 组：test / 无头能力（你主动问的）

### D1. 非阻塞跑帧

**现状**：`Show()` 阻塞跑循环。自检只能"跑 4 帧 → 截图 → 关窗"，逻辑塞在 `onRenderBoundTick` 里数字段。

**期望**：`PumpOnce()` / `RunFrames(n)`——跑完就返回，宿主拿回控制权。

**价值**：这是无头自检能从"跑一次看截图"升级到"CI 里跑 100 个断言"的前提。

### D2. 离屏渲染

**期望**：`RenderToTexture(path, w, h)`，不建窗口也能出图。

**价值**：现在依赖 `SDL_VIDEO_DRIVER=dummy`，换个机器就可能挂。

### D3. 帧内调度

**现状**：`main.cpp` 用 `g_firstFrameAction` 手工实现"第一帧跑一次"的命中探针。

**期望**：`RunAfterFrames(n, fn)` 或 `PostFrameTask(fn)`。

**价值**：这是 §5 里 SelfTest 插件能跑起来的关键之一。

### D4. 确定性时间步

**期望**：可注入 `delta`，或固定时钟。

**价值**：动画、主题过渡的截图在 CI 里才稳定，否则每次像素都不一样。

### D5. `RequestClose(int code)`

**现状**：`RequestClose()` 无参数，退出码由宿主自己算（`main.cpp` 返回 `g_failures`）。

**价值**：自检插件要能"报失败并让进程以非 0 退出"，否则 CI 拿不到信号。

### D6. 命中表可强制构建

**现状**：`QueryHit` 在 `Show()` 之前一律返回 null（命中表帧首才建）。

**期望**：`RebuildHitTable()` 可手动调，不必等帧。

**价值**：自检想在窗口出现前验证"这个位置点得到谁"，现在做不到。

### D7. 【建议】点击能力的基类抽象

**现状**：core 自检必须 `dynamic_cast<inking::InkingStaticButton*>` 才能调 `TriggerClick()`（`main.cpp` 四处）。换个控件类型自检就崩。

**期望**：`InkingWidget::Activate()` 之类的虚函数，或 `InkingScene::Activate(name)` 按名字触发。

**价值**：SelfTest 插件要通用，就不能知道具体控件类型。这条不修，自检插件必然和具体 UI 绑死。

## 4. 优先级建议

| 序 | 项 | 理由 |
| --- | --- | --- |
| 1 | **A5** 显式重建收集表 | 一条入口解 A2/A3 两个死结，成本最低、收益最大 |
| 2 | **A1** 动态组件进命中表 | 直接决定 core 要不要保留"到处重建" |
| 3 | **D1 + D5 + D6** | SelfTest 做成插件的最小可行集（配 D3 更好） |
| 4 | **B1** 交叉轴拉伸 | 砍掉大量宽度魔数 |
| 5 | **B3** 顶栏高度可查 | 把 §8 的全屏留白真正修掉 |
| 6 | **D7** 点击基类化 | 自检插件通用化的前提 |
| 7 | A2 / A3 / A4 | A5 落地后价值递减 |
| 8 | C1 / B2 / C2 / D2 / D4 / C3 | 表达力与体验 |

## 5. 关于「SelfTest 做成插件」

方向上我同意，而且它比放在 core 里更正确——理由有三：

1. **自检的断言对象是"当前这套 UI"**，而 UI 由面板插件决定。自检跟着 UI 走，就该和 UI 同层。
2. **符合你自己定的规矩**：core 里不放只有某个程序才需要的东西。而"断言三栏是 56/1224/40"显然只有这个 shell 才需要。
3. **换面板插件时可以不装自检插件**，宿主本体不受影响。

### 但它有两个前提，缺一不可

**前提一：core 必须补生命周期能力（D3 + D5 + D6 + D7）**

插件 entry 在**装配之前**跑（core 的两阶段：先注册、后建界面）。自检插件在 entry 里拿不到界面。它需要：

- 一个「装配完成后」的钩子（`onReady` / 首帧回调）
- 能拿到界面根（现在插件只能在 `create` 时拿到传进来的 `parent`）
- 能触发点击而不 `dynamic_cast` 到具体控件（D7）
- 能报失败并影响进程退出码（D5）

这四项都是**通用能力**，不是 test 专用——菜单插件、快捷键、拖拽都要同样的东西。所以补它们不算为测试开特例。

**前提二：core 侧必须留一个极小的冒烟检查**

这是 bootstrapping 问题，必须说清楚：

> 自检插件如果因为扫描器坏了、dll 加载失败、ABI 不匹配而**根本没被加载**，
> 那么"没有任何断言失败"会被误读为"全部通过"——**静默通过是最坏的结果**。

所以 core 里必须留一条极小的、不依赖任何插件的检查：

- 插件目录扫到了几个（0 个 → 失败）
- 至少一个插件加载成功（0 个 → 失败）
- 面板插件是否存在（不存在 → 明确告警）
- 退出码如实反映上述结果

这一条大约 30 行，不是"自检逻辑"，是"自检的前置断言"。它不能是插件。

### 还建议一条边界：自检插件只断言通用契约

如果自检插件硬编码 `"shell.root"`，那它就不是 core 的验收工具，而是 shell 的单元测试——换掉 shell 它必崩，等于把 `main.cpp` 现在的问题原样搬进插件。

建议这样切：

| 谁 | 断言什么 |
| --- | --- |
| 自检插件（通用） | 根节点铺满设计画布；每个注册的页面都能 mount 成功；每个注册的 region item 都能创建；换页后旧页消失、只剩一个页面；退出码如实 |
| 面板插件自己 | 三栏 56/1224/40 这类几何常量、抽屉展开宽度、具体节点名 |

后者属于面板插件自己的单元测试，不该由通用自检代劳。

### 落点建议

```
plugins/dev/selftest/     role 缺省，descriptor.depends 面板插件
                          plugin.json 里可加 "devOnly": true，发布构建时不装
```

用 `depends` 保证它在面板插件之后 entry；用 `onReady` 钩子（待补）在装配后跑断言。
