## 0. 结论（TL;DR）

0.4.0 迁移那轮（`docs/migration-task-book.md`，T-01~T-06）把绕路代码删干净了，但**删完之后没有护栏**：10 个自检模式、断言散在 4 个插件的 `ready` 里，全靠人手动循环跑。同时迁移过程中留下了三笔结构账（自检回调对没声明的插件也调用、设计尺寸四处双写、一个死常量）。

共切 6 个任务、分三批：**先立护栏（T-01/T-02），再清结构（T-03/T-04），最后适配 1080p（T-05/T-06）**。理由是每一刀都要靠前一批的 `ctest` 才知道有没有回归。

> T-05/T-06 是 2026-10-23 追加的：用户要求把设计画布从 1280×720 改成 1080p。
> 顺序上**先 T-04 收口、再 T-05 改数**——反过来只是把四处双写从 1280/720 复制成 1920/1080。

| 编号 | 任务 | 批次 | 对应来源 | 落点 | 代价 |
| - | - | - | - | - | - |
| T-01 | 把 10 个自检模式收成 ctest | 一 | §2-1 | `CMakeLists.txt` + `tools/selftest.bat`（新增） | 中 |
| T-02 | 退出码改成失败项数 | 一 | §2-2 | `host/main.cpp` 末尾 | 低 |
| T-03 | 自检回调只对声明了 `onReady` 的插件调用 | 二 | §2-3 | `include/sdk/GoldingPluginBase.h` | 低 |
| T-04 | 设计尺寸收成单一来源 | 二 | §2-4 | `plugins/core/shell/src/ShellPlugin.cpp`、`plugins/core/appdrawer/` | 中 |
| T-05 | 设计尺寸改成 1080p | 二 | 用户指令（2026-10-23） | `host/main.cpp` | 低 |

设计取向两条：

1. **护栏先立，且要先能证明它会红**。验收不是"ctest 全绿"，而是"注入一个失败项之后 ctest 变红、退出码等于失败项数"——只绿不红的护栏等于没有。
2. **能落在插件里的不落在 core**。面板几何归面板（上一轮已定），这一轮继续：设计尺寸的唯一来源是宿主那次 `SetDesignSize`，插件从父节点量，不再各自抄常量。

## 3. 第一批：回归护栏

- T-01 把 10 个自检模式收成 ctest-已完成（2026-10-23，ctest 10/10；`tools/selftest.bat` 拼错模式返回 1。细目见 `docs/TASK-CORE-UPING.md` 同名任务）

### T-02 退出码改成失败项数

- **状态**：未开始
- **移交**：已移交 `docs/TASK-CORE-PLUGINS.md` 的 T-02（同一件事，方案不变）。**完成以那边为准**，完成时两边同改状态。
- **落点**：`host/main.cpp:262`

**准备怎么改**

`return g_failures == 0 ? 0 : 2;` 让"红了 1 条"和"红了 9 条"在 CI 里没有任何区别，也和 `docs/HANDOVER.md` §2 写的"退出码 = 失败项数"不符。三个候选：

| 方案 | 做法 | 代价 | 结论 |
| - | - | - | - |
| A | `return g_failures > 125 ? 125 : g_failures;` | 125 是 shell 的退出码上限（与技能自带的 `check_task_book.py` 同一口径） | **推荐** |
| B | 保持 0 / 2 两档 | 0 改动；但"几条红"要靠 grep 输出 | 不做（CI 只能知道"红了"） |
| C | 写进一个 `selftest_report.json` 让 CI 解析 | 多一份产物格式要维护 | 不做（超需求） |

**大致改动逻辑**

1. `main.cpp` 末尾的 return 改成按失败项数返回，并夹到 125。
2. 同一处补一句注释：为什么是 125（不是 255）——`cmd` 与 shell 的上限口径，和技能脚本一致。
3. **不能反的一步**：`g_failures` 的累加必须已经包含插件 `ready` 的返回值（`g_failures += app.notifyReady()` 在它之前一行）——否则插件里的失败不进退出码，T-01 的 ctest 会绿灯放过。

**与改动前对比**

| 场景 | 改动前 | 改动后 |
| - | - | - |
| 全绿 | 退出码 0 | 退出码 0（**不变**） |
| 红 1 条 | 退出码 2 | 退出码 **1** |
| 红 7 条 | 退出码 2 | 退出码 **7** |
| 红 300 条 | 退出码 2 | 退出码 **125**（夹住） |
| `--stay` 关窗口后的返回值 | `g_failures == 0 ? 0 : 2` | 同上规则——所以 `run.bat` 的 `if errorlevel 1` 依旧生效，**不变** |

**验收**：临时把 `ShellPlugin.cpp` 里"主体接在顶栏之下且高 680"的 `680` 改成 `681`，`ctest` 应报 1 个 test 失败且该 test 退出码为 `1`；改回后恢复 10/10。这条同时是 T-01 护栏的"会红"证明。

**风险与回退**：如果有外部脚本把"退出码 2"当作"自检失败"的判据，改成 1 之后会认不出来；回退 = 单行改回 `? 0 : 2`。

## 4. 第二批：结构清理

### T-03 自检回调只对声明了 `onReady` 的插件调用

- **状态**：未开始
- **移交**：已移交 `docs/TASK-CORE-PLUGINS.md` 的 T-03。**方案已换**：本任务假设的"探测是否重写了 `onReady`"对虚函数做不到，改为"`Ready` 默认返回 `-1`"的返回值约定；落点也从 `GoldingPluginBase.h`（已删除）变成 `GoldingPlugin.h`。完成以那边为准。
- **落点**：`include/sdk/GoldingPluginBase.h`（`PluginSpec::descriptor()`）

**准备怎么改**

`descriptor()` 无条件设 `ready = &callReady`，而 `callReady` 在没有 `onReady` 时返回 0。于是宿主侧"有没有 ready 可调"这个判断永远成立，9 个插件都打一行 `[host] 装配后自检：<名字>`，其中 5 行后面什么都没有——**噪音会养出"这行不重要"的阅读习惯**，正好盖住第 6 个真有断言的插件。

| 方案 | 做法 | 代价 | 结论 |
| - | - | - | - |
| A | `_descriptor.ready = _onReady ? &PluginSpec::callReady : nullptr;` | 一行；宿主侧已有的 `ready == nullptr` 过滤自然生效 | **推荐** |
| B | 宿主侧判断"这个插件有没有断言" | 宿主没有这个信息 | 做不到 |
| C | 给 5 个没断言的插件也写 `onReady`（哪怕空） | 制造假工作，且"空断言"比"没有断言"更难发现 | 不做 |

**大致改动逻辑**

1. `descriptor()` 里按 `_onReady` 是否为空决定填不填 `ready`。
2. 注意**顺序**：`descriptor()` 由宏在 `golding_plugin_descriptor()` 里调用，而 `.onReady(...)` 的链式调用在静态初始化期就完成了——所以读 `_onReady` 时它已定型。反过来（先读后链）会永远拿到 nullptr。
3. **不能反的一步**：不要同时改 `callReady`（它的空值判断留着，作为双保险）。

**与改动前对比**

| 场景 | 改动前 | 改动后 |
| - | - | - |
| 启动输出里的自检标题行 | 9 行（5 行后面没有断言） | 4 行（selftest / shell / appdrawer / theme） |
| 有断言的插件 | 正常回调 | **不变** |
| 没有 `onReady` 的插件 | 被调一次空回调 | 完全不被调（`ready == nullptr`） |
| ABI | v8 | **不变**（只是填 nullptr 而不是填地址，结构体没动） |

**验收**：`golding_host.exe` 的输出里 `[host] 装配后自检：` 出现 **4** 次；`ctest` 10/10 仍绿。

**风险与回退**：`PluginSpec` 若有人在 `descriptor()` 之后才调 `.onReady(...)`（唯一入口是静态初始化期的链式写法，正常不会），ready 会被漏填；回退 = 恢复无条件填 `&callReady`。

## 5. 第三批：1080p 布局适配

### T-06 页面布局适配 1080p

- **状态**：未开始
- **移交**：已移交 `docs/TASK-CORE-PLUGINS.md` 的 T-08（候选表与顺序沿用本任务）。**完成以那边为准**；那边多一条本任务没有的约束：home 的按钮几何现在写在 `kLaunchConfig` 的 JSON 里，改布局要连它一起改。
- **落点**：`plugins/core/home/`、`store/`、`settings/`、`magic/` 的 `createXxx`，`plugins/core/appdrawer/` 的 `createDrawer`

**准备怎么改**

T-05 只把画布变成 1920×1080，页面里仍是按 1224×680 写的绝对坐标：settings 的行面板固定 900 宽、home 的 `art` 钉在 x=732、appdrawer 是 5 列 ×224 的固定网格、magic 画布 900×290。于是 1080p 下内容挤在左上、右侧空 ~900px、下方空 ~360px。

三个候选：

| 方案 | 做法 | 代价 | 结论 |
| - | - | - | - |
| A | 页面根改成**布局容器**（Stack / Grid + `fillMain` / `Stretch`），间距交给 padding / margin | 治本：换任何分辨率都跟着走；但 5 个页面都要重排，且 magic 画布是"自己按尺寸画"的，不适用布局 | **推荐**（按页拆开做） |
| B | 保留绝对坐标，按比例放大量（72→108、900→1350） | 快；但比例系数成为新魔数，下次换分辨率再来一遍 | 不做（只是把双写换成三写） |
| C | 场景级等比缩放（让 1080p 显示 720p 的内容） | 一次到位；但字体会被拉糊、magic 环变虚，且丢掉"1080p 更清晰"的收益 | 退路（要"今天就能看"时用它） |

**大致改动逻辑**

1. 先做 **home 一页**：根是 `PanelData` + `Stack`（纵向），标题/副标题/按钮一组、`art` 一组，`art` 用 `selfAlign = End` 贴右；跑 10 模式 + 截图确认。
2. 再依次 settings / store / appdrawer（网格改成按内容区宽算列数，或让 `kColumns` 随宽度取）、magic（**不改**：画布 900×290 是它自己的设计尺寸，只把它在页面里居中）。
3. 每页各自加一条断言：**最右侧可见子节点的右边缘 ≥ 内容区右边缘 − 64**（"没有大片留白"这件事唯一的量化口径）。
4. **不能反的一步**：一页一页来，每页改完立刻跑 10 模式。5 页一起改，红了分不清是布局错还是断言错；而且页面根一旦被拉伸，里面按绝对坐标摆的子节点不会跟着动——这是最典型的"改了一半"。

**与改动前对比**

| 场景 | 改动前 | 改动后 |
| - | - | - |
| settings 的行面板 | 固定 900 宽、贴左（右侧空 ~960px） | 吃满内容区宽（1864），**表头与值贴两端** |
| home 的标题 / 按钮 / `art` | 72,140 / 72,268 / 732,130 三处钉死 | 标题贴左上、按钮在其下、`art` 贴右（相对排布） |
| appdrawer 网格 | 固定 5 列 ×224（右侧空 ~744px） | 列数按可用宽度算，末列右边缘贴内容区 |
| magic 画布 900×290 | 贴左 | **尺寸不变**（画布自己的设计），只在页面里居中 |
| 1280×720 下的观感 | 现在的样子 | **不变**（相对布局在 720p 下结果一致） |

**验收**：每页一条"最右侧元素右边缘 ≥ 内容区右边缘 − 64"的断言（在各自 `ready` 里，跟着 10 模式跑）；`--page=0..3` 四张截图里右侧留白 ≤ 64px。

**风险与回退**：页面根容器化会改掉"页面根尺寸 = create 时刻父级尺寸"这条隐含假设，而 4 个页面都在用绝对坐标摆子节点——**改一半就会散**；回退 = 每页独立（各自一个 `PanelData` 分支），哪页没改好就把该页退回绝对坐标，不影响别页。

## 7. 明确不做（避免反复讨论）

| 不做的事 | 原因 |
| - | - |
| 自检加"只在开发构建跑"的开关 | 断言只是几次几何比较，代价可忽略；且现在没有"发布构建"这个概念。真要做就加 `GOLDING_SELFTEST` 编译开关，等有对外发布需求再说（届时它本身要一个任务） |
